# Notifications and communication module

## Architecture

The module separates communication content (`Notification`), normalized audience rules, immutable recipient snapshots, per-channel delivery attempts, formal announcements, conversations/messages, attachments, preferences, templates, policy, device tokens, and audit history. Every school request derives its tenant and sender from the authenticated token. Student and parent portal identities use tenant-scoped principal keys because those accounts are stored in `Student` in the existing application.

The legacy `UserWidgetNotification` and `AcademicNotification` tables remain intact. `prisma/backfillLegacyCommunication.js` copies their history into the unified model idempotently and preserves timestamps/read state. New homework, resource, attendance, fee-payment, fee-reminder, and calendar events write through the unified service.

In-app delivery is real and tracked. Authenticated server-sent events provide live delivery for connected clients; polling remains as a resilient UI fallback. Email, SMS, push, and WhatsApp use provider boundaries and are recorded as `SKIPPED` until real credentials/adapters exist—success is never fabricated. Failed configured deliveries use capped exponential retry.

## Setup

Development:

```bash
npm install
npx prisma validate
npx prisma migrate dev
npx prisma generate
npm run backfill:communication
npm run seed:communication
npm test
```

Production:

```bash
npx prisma migrate deploy
npx prisma generate
npm run backfill:communication
```

The scheduler is enabled by default and checks scheduled publications, expiry, and deliveries every 60 seconds. Configure `COMMUNICATION_JOBS_ENABLED` and `COMMUNICATION_JOB_INTERVAL_MS` as needed.

## API and UI

The backend exposes notification state/count, announcement lifecycle/analytics, secure conversations and message lifecycle, preferences, device tokens, templates, policy, recipient directory, attachments, delivery reports, jobs, and an authenticated event stream under `/api`. The frontend provides `/notifications` and `/communication`, with role-aware navigation, announcement composition, inbox, recipient discovery, preferences, and admin analytics.

## Manual verification

The standard demo foundation uses `admin@greenvalley.edu.in` with password `admin123`. Portal accounts retain credentials generated by the existing academic seed.

1. Sign in as admin and publish a school-wide announcement.
2. Confirm the resolved recipient count and in-app delivery analytics.
3. Sign in as a student/parent and verify child context, read state, and acknowledgement.
4. Sign in as a teacher; verify an assigned section is accepted and an unrelated section is rejected.
5. Start a parent-teacher conversation and verify a non-participant cannot read or post.
6. Disable an optional preference and confirm new optional in-app delivery is muted; confirm emergency delivery still appears.
7. Schedule a notice and run `POST /api/communication/jobs/run` as admin or wait for the scheduler.
8. Inspect failed/skipped external channels in delivery analytics.

## Provider status and limitations

- In-app/database: implemented.
- Live SSE: implemented in-process; use a shared event bus when horizontally scaling.
- Email/SMS/push/WhatsApp: adapter boundary and accurate skipped/failure tracking implemented; vendor adapters are intentionally not fabricated.
- Files: secure metadata validation and participant/owner authorization are implemented. Production storage should issue signed private URLs; the current upload provider still supplies the URL.
- Exam/result events are supported as categories/templates and seed data, but this repository has no dedicated exam/result module to emit domain events yet.
- Platform-owner broadcasts are kept out of school-private APIs; a dedicated platform campaign UI/provider is not included.
